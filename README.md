# Лабораторная работа №1 — Redis / NoSQL

## Предметная область

Разрабатывается система уведомлений для **небольшого кинотеатра с одним кинозалом**. В системе администратор формирует расписание показов фильмов и категории, а авторизованные пользователи получают информацию о фильмах и общие уведомления о ближайших премьерах. Бронирование билетов в рамках работы не реализуется.

## PostgreSQL

PostgreSQL используется как основное постоянное хранилище данных:

- **User** — пользователи системы;
- **Role** — роли `ADMIN` и `USER`;
- **Category** — категории фильмов;
- **Movie** — фильмы и время их показа.

Связи между сущностями:

```text
User M:N Role
Category 1:M Movie
```

## Redis

Redis используется для хранения временных и часто запрашиваемых данных, а также для реализации механизмов конкурентного доступа.

### Кэширование категорий

Часто запрашиваемые категории хранятся в Redis в качестве кэша. При первом запросе категория загружается из PostgreSQL и сохраняется в Redis на 5 минут. При повторном запросе данные берутся из кэша без обращения к PostgreSQL.

```text
category:<id>
```

### Уведомления

Уведомления о ближайших премьерах хранятся в Redis с использованием **TTL**. Уведомление создаётся за 3 часа до начала фильма и автоматически удаляется после начала показа.

Ключ:

```text
notification:<id>
```

### Кэширование расписания фильмов

Список фильмов (`GET /movies`) кэшируется на каждом узле приложения так же, как категории — cache-aside, ключ `movies:all`, TTL равен `SCHEDULE_PROPAGATION_DELAY_MS`. Кэш инвалидируется на своём узле сразу после успешного создания/изменения фильма.

### Пул соединений к Redis

`RedisService` больше не держит одно-единственное TCP-соединение к Redis: вместо этого он создаёт пул из `REDIS_POOL_SIZE` независимых `ioredis`-клиентов к «своему» (локальному для этого узла) Redis и выбирает клиента для каждой команды по кругу (round-robin). Каждый клиент настроен на переподключение (`retryStrategy`, `maxRetriesPerRequest`, `connectTimeout`), поэтому подвисшая команда или обрыв одного соединения не останавливают всё приложение — остальные соединения пула продолжают обслуживать запросы.

### Распределённая блокировка расписания (Redlock)

В реальной системе у каждого узла приложения (условно — города) свой, независимый Redis, и данные в нём могут быть неактуальны. Поэтому лок на изменение расписания дня, при добавлении или изменении фильма, — больше не обращение к одному центральному Redis, а классический алгоритм **Redlock**: лок считается взятым только при получении кворума (большинства голосов) от заранее заданного списка независимых redis-узлов (`REDIS_NODES`).

```text
lock:<date>
```

Как и раньше, лок ставится с TTL и без повторных попыток — если кворум не набран, запрос сразу получает `409 Conflict`.

### Eventual consistency при изменении расписания

При изменении времени показа фильма (`PATCH /movies/:id`, только `ADMIN`) сразу после захвата распределённого лока, ещё до записи в PostgreSQL, на **все** redis-узлы рассылается флаг:

```text
editing:<date>
```

Пока этот флаг жив на локальном Redis узла (TTL = `SCHEDULE_PROPAGATION_DELAY_MS`, имитация задержки репликации между «городами»), `GET /movies` на этом узле не отдаёт расписание, а возвращает `{ editing: true, message: 'Ведутся правки в расписании' }`, не полагаясь на потенциально устаревший кэш. Узел, на котором проходило изменение, инвалидирует свой кэш сразу и видит свежие данные без задержки. TTL кэша списка фильмов намеренно равен TTL флага — это упрощение для лабораторной работы, не гарантия промышленного уровня согласованности, но оно гарантирует, что к моменту снятия флага локальный кэш узла тоже устареет и будет перечитан из PostgreSQL.

### Запуск нескольких независимых узлов (демонстрация)

```bash
docker-compose up -d   # поднимает 3 независимых redis-контейнера: 6380, 6381, 6382

PORT=3031 NODE_ID=node-1 LOCAL_REDIS_PORT=6380 REDIS_NODES=localhost:6380,localhost:6381,localhost:6382 npm run start:dev
PORT=3032 NODE_ID=node-2 LOCAL_REDIS_PORT=6381 REDIS_NODES=localhost:6380,localhost:6381,localhost:6382 npm run start:dev
PORT=3033 NODE_ID=node-3 LOCAL_REDIS_PORT=6382 REDIS_NODES=localhost:6380,localhost:6381,localhost:6382 npm run start:dev
```

Все три инстанса используют одну и ту же PostgreSQL (источник истины), но каждый — свой Redis для кэша и свой голос в кворуме Redlock.
